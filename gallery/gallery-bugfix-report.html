The first pass fixed §1–§16 and filed four new bugs (A–D) found along the way. Those four are now fixed too, in four more gallery.ui commits, and all four carry a regression spec that was verified to fail against the pre-fix code. Section 05 is new; the tiles, section 06 and section 09 have been updated. Sections 03 and 04 describe the first pass and are unchanged.

01How the work was run

Subagent-driven development: one implementer per bug, then an independent reviewer per bug, with a ledger surviving between them. Across both passes: 19 implementation tasks, 19 reviews, two fix rounds.

Each bug became a task brief with the cause pre-diagnosed from source, so implementers never had to re-derive it. Each finished commit went to a fresh reviewer that got the brief, the implementer's report, and the diff — and was told to verify claims against the actual files rather than trust the report. Reviewers were explicitly forbidden from being told what not to flag.

Twelve of thirteen tasks passed review first time. One (§14, the SignalR scoping bug) came back with a real defect and went through one fix round; details in Where subagents pushed back.

Ordering was chosen so no two concurrent agents touched the same file. admin-collections alone was touched by three separate bugs (§2, §10, §7), so those were serialised and each implementer was told the others' commits already existed and must not be reverted or swept in.

The second pass (A–D) ran the same way: six more tasks, six reviews, one more fix round on bug D. Two changes to how it was run, both because of what the first pass revealed. First, every fix got a regression spec, and each spec had to be demonstrated to fail against the pre-fix code — not merely to pass against the fixed one. Second, where an implementer or reviewer raised a substantive objection, I verified it in the source myself before acting on it, rather than relaying it downstream. That mattered twice: once to confirm a reviewer's finding was real before requiring a fix, and once to confirm an implementer's deviation from my own brief was correct.

02Decisions you made, and why they mattered

Six questions had no single defensible answer, so I asked before dispatching the work. Each one changed the resulting code — and one of them corrected me.

§11 — deleting a card that still has articles

Your choice

Reject with 409 Conflict and a message naming the blocking article count — not cascade-delete, not null out CardId.

Why it mattered

All three were implementable. Cascade would have destroyed articles on a single click; nulling CardId would have orphaned them into a state the UI can't surface. Your choice is the only one that loses no content. It also decided the shape of the test: it now asserts a 409 and the exact message, rather than a 204 and a side effect.

§16 — where an exhibit click should land

Your choice

Always the Wall, via an explicit section=wall on the link — not "restore the remembered section".

Why it mattered

The buggy code was reaching for remembered-section behaviour and corrupting it. Restoring that intent was the tempting fix, but it makes the landing section depend on history, which is untestable without seeding localStorage. Your choice satisfies test-plan §2.4 directly and made the assertion a one-liner. It also produced the one full-suite regression — a second spec asserted the old href — which is exactly the kind of thing that should fail loudly.

§14 / §10 — how deep to fix

Your choice

UI fix and narrower API broadcasts, rather than UI-only.

Why it mattered

This is the decision that needed the most care, because I had verified something that constrained it: MainHub.Join() adds a connection to only the userId group, and exhibit-id groups are joined only via SwitchTeam, which the client invokes only on reconnect. So a compound {exhibitId}-{userId} group has no join path — narrowing a broadcast to one would have delivered events to nobody, converting a visible bug into a silent one.

I passed that constraint into the task and made "leave a broadcast unchanged and say why" an explicitly acceptable outcome. The result honours your choice where it is safe: the UI filter is load-bearing and stands alone, and the API change is a genuine but conservative one (Distinct() on a fan-out that was sending every card event to the same user N times). Two handlers were deliberately left alone, with the join-path tracing to justify it.

§13 — migration for the mistyped EF navigation

Your choice

Fix the type, generate a migration, keep it only if Up() does real work.

Why it mattered

This was the right instinct: it verified rather than assumed. The generated Up() turned out to drop a phantom FK (FK_articles_cards_exhibit_id) that exists nowhere in migration history — an artefact of the wrong model — and re-add the real one identically. So it was a no-op and was discarded; the regenerated model snapshot was committed so the next developer's migration stays clean. Had we skipped the check, we'd have either shipped a pointless migration or left the snapshot lying.

D — how to fix the shared TeamStore (second pass)

Your choice

Track which exhibit the store was loaded for and compare against that — rather than clearing the store whenever the active exhibit changes, which is what the bug document itself suggested.

Why it mattered

The document's suggestion would have worked and would have let the predicate become a plain exhibitId comparison — but the team store is shared, and admin's toggleExpand calls setActive(id) immediately before loadByExhibitId(id). Clearing on active-exhibit change would have made the admin Teams panel silently dependent on that call ordering. Your choice left every existing write path alone and made the predicate exact instead of heuristic. It also turned out to be the harder option to get right — see bug D in the follow-on section for the two traps it took a review and a fix round to clear.

Coverage — which fixes get a regression spec (second pass)

Your choice

All four. You overrode my initial recommendation, which was to cover only A and B and skip C and D as having no observable UI signal.

Why it mattered

I was wrong, and it's the most consequential correction in this pass. Both C and D turned out to be observable — but only via non-obvious signals that had to be found rather than assumed. C's spec mutates a sibling exhibit and asserts that sibling's own cells change before checking the panel, which is what makes it a real test instead of a vacuous one. D's spec required capturing websocket frames to first establish that a foreign TeamCardUpdated even reaches the browser. Neither would exist if I'd had my way, and the two hardest bugs in this pass would have shipped with no regression cover at all.

§9 — constraint violations were reported as 500 87b546d

The middleware already classified the Postgres SQLSTATE correctly and built a clean, user-safe message for each case — then threw it away. TransformPostgresException returned a plain InvalidOperationException, which doesn't implement IApiException, so GetStatusCodeFromException fell through to its 500 default.

Fix. Added ConflictException (409) and BadRequestException (400) alongside the existing IApiException types, and used them in both the Postgres and SQL Server transforms. Unique violations (23505 / 2601 / 2627) → 409; FK and check violations (23503 / 23514 / 547) → 400. Message text unchanged.

Why this fixes it. The classification work already existed and was correct; only the carrier type was wrong. Giving it a type the middleware actually consults makes the existing logic reachable. This also became the foundation for §6 and §11.

§6 (API half) — malformed upload 500'd e008baa

UploadJsonAsync called JsonSerializer.Deserialize with no try/catch, and JsonException doesn't implement IApiException, so a malformed client file became a server error.

Fix. Wrapped the deserialise in both CollectionService and ExhibitService, throwing the new BadRequestException. Also guards the null-after-parse case ("valid JSON, not a collection file").

Why this fixes it. A malformed client upload is a client error. 400 lets the UI distinguish "your file is bad" from "the server broke" — which is what made the UI half (§6, 4d22a85) able to show a useful message.

§8 — download 500'd when Description was null 9e2dda8

The download filename was built from collection.Description.ToLower() with no null guard — and description is optional on create, so NullReferenceException → 500. The filename was also derived from Description rather than Name, which is odd in its own right.

before
Description.ToLower().EndsWith(".json") ? Description : Description + ".json"
after
Name (falling back to Id when blank), honouring Description only when it already ends in .json

Why this fixes it. .ToLower() now sits behind a Description != null && short-circuit, so it can never run on a null; and because the base name comes from Name with an Id fallback, every combination of null/blank Name and Description still yields a usable .json filename. Reviewer traced all four combinations.

§4 — downloaded collection couldn't be re-imported f50b391

My favourite bug in the set, because the two-line fix is nothing like the symptom.

Cause. DownloadJsonAsync loaded the collection tracked — its Collections query lacked AsNoTracking(), unlike the sibling Cards/Articles queries right below it. Authorization had already run on the same scoped DbContext and loaded that user's CollectionMembershipEntity rows, so EF's identity map attached them to the tracked collection's Memberships navigation without any Include(), and ReferenceHandler.Preserve serialised the whole graph — nested UserEntity included — into the export. On import, that graph was re-Added, EF found it was already tracking an entity with the same key, and SaveChangesAsync threw.

Why it looked intermittent. Claims are cached for 60s. Cache miss → membership rows get loaded → export embeds them → upload 500s. Cache hit → export is clean → upload works. So the same endpoint produced a 7308-byte poisoned file or a 377-byte good one depending on request-local EF state.

Fix. AsNoTracking() on the download query — matching what ExhibitService already did, which is precisely why the exhibit round-trip worked and the collection one didn't. Plus nulling Memberships on import, so files already exported in the bad state can still be imported.

Why this fixes it. It removes the mechanism rather than the symptom: with no tracking there is no identity-map attachment, so nothing to serialise and nothing to collide on re-add. It also makes exports deterministic, which matters independently — a downloaded collection is now a stable artifact. Verified live: 386 bytes every time, 0/6 upload failures.

§11 — card delete 500'd when the card had articles 784ae3d

DeleteAsync removed the card with no check for dependent articles and no cascade configured, so Postgres rejected it. The 23503 branch then reported "Referenced entity does not exist" — actively misleading, since the referenced entity does exist, which is exactly why the delete failed. cardToDelete was also unguarded, so deleting a nonexistent id threw.

Fix (your 409 decision): null-guard → EntityNotFoundException<Card> (404); count articles with CardId == id and, if any, throw ConflictException naming the count with correct singular/plural.

One judgement call worth recording. The count deliberately does not filter on ExhibitId, even though the display path (GetByCardAsync) does. The reviewer verified the FK FK_articles_cards_card_id is onDelete: Restrict with no exhibit_id condition — so Postgres blocks on any matching row. Filtering to match the display would have under-counted and let the original 500 straight back in for exhibit-scoped articles.

§13 — ArticleEntity.Exhibit was typed CardEntity 46cfa54

Copy-paste from the Card pair two lines below, so EF mapped Exhibit as a second relationship to Cards using ExhibitId as the FK. The real database constraint was correct all along — FK_articles_exhibits_exhibit_id points at exhibits. The C# model and the schema disagreed, and the model was the wrong one.

Fix. Retyped to ExhibitEntity; generated migration was a verified no-op and discarded; regenerated snapshot committed.

Why this fixes it. Nothing read the navigation as an object (all consumers use the scalar ExhibitId), so this is latent-correctness work: it stops the snapshot from recording a relationship that does not exist, which is what would have bitten the next person to run migrations add or to write Include(a => a.Exhibit). No inverse collection was added, matching how the sibling Card/Collection relationships are declared.

§14 (API half) — duplicate card events per user 7797209

CardHandler.GetGroups collected users across every team of every exhibit in the card's collection. The unique index on TeamUsers is on the pair (UserId, TeamId), so a user on teams in several exhibits of one collection appeared once per exhibit — and received N copies of every card event.

Fix. Distinct() on the UserId projection.

Why this is safe. It removes only repeated identical GUIDs, so the addressed group set is bit-identical and no recipient can be lost. This was the one API-side narrowing that was provably safe given the join-path constraint — see §07.

§1 — Exhibits table sorting and pagination were both dead ee3c613

The table sits inside @if (!isLoading && selectedCollectionId), while the view queries resolved once in ngAfterViewInit. selectedCollectionId starts '', so at that moment the table did not exist, both @ViewChilds were undefined, and dataSource.sort/.paginator were permanently set to undefined.

The deceptive part: aria-sort still cycled correctly, because matSort on the header tracks its own state. Only the datasource was never connected — so the header looked functional while the rows never moved.

Fix. Setter-based view queries that reassign whenever the table appears, and the dead ngAfterViewInit removed. ({ static: false } alone would not have worked — the assignment still runs once.)

Why this fixes it. The reviewer verified from Material's own source: sortChange is of(null) when _sort is unset, so _orderData short-circuited entirely. Once the real directive instance is assigned, click-driven sort feeds the data pipeline and reorders every subsequent emission. The paginator likewise only clamps pageIndex when out of range, so page position survives store emissions.

§10 — Collections table had no trackBy 9f7603a

The component rebuilt its list from fresh object clones on every store emission (push({ ...collection })) and reassigned dataSource.data. With no trackBy, Angular destroyed and rebuilt every row; the expanded Cards/Articles detail is behind @if (element.id === expandedCollectionId), so the panel came back collapsed — mid-edit, for every admin, whenever anyone anywhere changed any collection, card or article.

Fix. trackBy keyed on collection.id.

Why one binding is enough. This one deserved scrutiny, because the table uses multiTemplateDataRows — the same item renders two rows, so the key is duplicated. The reviewer confirmed from CDK source that trackBy is a single table-level input shared by all row definitions, and that Angular's differ resolves duplicate keys by position via _DuplicateItemRecordList, so the normal row and detail row each re-match their own prior record. With the row preserved, forEachIdentityChange patches the existing view instead of recreating it, and the panel survives.

§7 — a late loadMine() could wipe the admin list 4fc3f98

load() (/api/collections — everything) and loadMine() (/api/my-collections — just the user's) both ended in the same unconditional whole-store replacement. With both in flight against one store slice, whichever response landed last won. Navigating home → Administration fires loadMine() then load(); if my-collections resolved second, the admin table collapsed from 46 rows to 3.

Fix. A single monotonic request token shared by both methods, captured before the request is issued and compared on arrival. Stale responses are dropped — including the error paths, which also called set([]); a stale error could blank the list just as a stale success could replace it. Also removed a duplicate GET /api/collections that fired on every admin visit.

Why this fixes it, and why not the "cleaner" option. Splitting the store slice per scope is the tidier design but a much larger refactor; the token closes the actual race with a change small enough to review confidently. The reviewer traced routing independently to confirm admin-collections can never mount without admin-container, which is what makes removing the duplicate fetch safe.

§16 — state written during change detection 0a37a10

getQueryParams() called uiDataService.setSection(exhibitId, Section.archive) — a state write — and was invoked from a template binding, once per rendered row. So merely rendering My Exhibits rewrote every exhibit's remembered section in localStorage. The link carried no section, and startup read the remembered value, so the click could never land on the Wall.

Fix (your always-the-Wall decision): the method is gone, the binding is a pure object literal carrying section: Section.wall.

Why this fixes it. Two things at once — the impure binding is eliminated, and the destination is explicit rather than inferred from state the render had just corrupted. The reviewer verified Section.wall's runtime value is 'wall' and that startup compares === Section.wall, since a casing mismatch would have silently reproduced the original bug.

§5, §2, §6-ui, §15 — the smaller four 5f08f25 · ca9acf5 · 4d22a85 · 8fb05c7

§5 — admin-teams crashed on a null short name. The email case of the comparator was null-guarded; the default/shortName case was not, and ShortName is nullable. Because the team store is global and re-sorts on every emission, one such team made the whole list throw mid-render and show nothing. Guarded the same way email already was.

§2 — the Copy button was a no-op. copyCollection(id) called permissionDataService.loadCollectionPermissions() and never copied. The correct call already existed, unused. Now calls collectionDataService.copy(id), mirroring admin-exhibits. The reviewer confirmed removing the permissions reload is safe — a freshly copied collection has no per-collection claim entry either way, so the action buttons fall through to the system-level check.

§6 UI half — invalid uploads failed silently. uploadJson handled the error with a callback that only reset loading state, so it never reached Angular's global ErrorHandler — the only thing that opens the system-message sheet. No sheet, no snackbar, nothing. Now shows the API's message (camelCase, per §3) in both the collection and exhibit services.

§15 — a share gave no confirmation. A bare .subscribe(), and archive.component.ts contained zero MatSnackBar references, so a successful share and a silently-failed one looked identical. Now both paths report, and the dialog closes only on success so a failure can be retried. The reviewer checked every settle path for a stuck-open dialog and confirmed loading state clears either way.

05The 4 follow-on bugs (A–D)

Found while fixing §1–§16 and filed rather than fixed, because each belonged in its own commit. Now fixed, in four more gallery.ui commits — and unlike the first pass, every one carries a regression spec proven to fail against the pre-fix code.

UIA & B — null-name team crashesb3bce54, 5eaa8b2

Cause

Team.name and Team.shortName are both string | null in the generated model. §5 guarded the default/shortName arm of the sort switch; the case 'name' arm and the filter predicate were left unguarded, deliberately, to keep that commit to one defect.

Why it blanked the whole list

The component re-sorts on every team-store emission, so the TypeError escaped Array.sort and sortedTeams was never reassigned — the template rendered zero rows, not just a misplaced one. That is the symptom the specs assert, which makes them strictly stronger than a crash check.

Verified reachable, not assumed

I probed the live API first: POST /api/teams with name omitted or explicitly null returns 201 and reads back as null. Had it rejected them, both bugs would have been unreachable in practice and the right answer would have been to say so rather than write specs.

One thing the specs deliberately assert

A null-name team must still match the filter on its shortName. A guard that neutralised the whole predicate would stop the crash while silently breaking search — passing a "doesn't throw" test while being wrong. The reviewer hand-traced all five null/empty combinations to confirm the implementation takes the independent-OR-branches form.

UIC — Exhibits table row rebuildf585bdf

Cause

Without trackBy, CdkTable's differ has no stable row identity, so every exhibit-store emission diffs each row as removed-then-added and destroys its view. That matters here because the sub-panels inside the expanded detail row are mat-expansion-panels with no [expanded] binding — their open state lives in the destroyed DOM, so the panel comes back collapsed and any work in progress in it is lost.

The interesting question, answered from source

The table is multiTemplateDataRows, so each exhibit backs two rendered rows and a bare item.id returns the same key for both. A reviewer traced the installed @angular/cdk and @angular/core to confirm that is correct rather than a duplicate-key bug: DefaultIterableDiffer supports duplicate track keys via _DuplicateMap, resolving the two consecutive render rows to distinct records. Since trackBy is a single table-level input consuming the already-interleaved render rows, binding once is not a style choice — it is the only API surface that exists.

Proven non-vacuous two ways

A trackBy spec can pass for the wrong reason if the store emission never actually reaches the component. So the spec mutates a sibling exhibit and asserts that sibling's Move/Inject cells change before touching the panel — those cells are re-rendered only by the subscription under test. Review confirmed the ordering is load-bearing by emptying the SignalR handler: the spec then failed at the guard rather than passing vacuously.

UID — TeamCard events scoped by store contents4fc3104

Cause

§14's predicate resolved a TeamCard's exhibit through its Team, and when the team was absent it guessed "stale vs foreign" by asking whether the store held any team of the active exhibit. The team store is shared — admin's loadByExhibitId writes it too, and nothing clears it on exhibit exit — so its contents are not a reliable statement about the active exhibit.

The fix, and why not the obvious one

It records which exhibit the store was loaded for rather than clearing the store on exhibit change (this document's original suggestion). Clearing shared state that admin also writes would have made the admin Teams panel dependent on call ordering inside toggleExpand.

Where this nearly went wrong — twice

The first revision also cleared the marker on load entry. That looked safer and was worse: home-app re-fires loadMine() on every query-param emission — every Wall/Archive toggle, every card click — so it opened a one-RTT window accepting foreign TeamCards on essentially every navigation, where the old code rejected them. I verified that re-fire in the source before requiring its removal.

Removing it then exposed a second trap the implementer caught and I had not asked for: with no entry clear, a failed load following a successful one leaves the marker confident over an emptied store, and the predicate rejects every TeamCard for that exhibit. So the error paths now clear it explicitly. Final discipline: set on success, cleared on error, cleared in unload(), untouched in flight.

What it deliberately does not fix

When the store describes some other exhibit — the literal shape this document filed as D — the predicate still accepts. The store genuinely cannot answer whether a team of the active exhibit exists, and 8b85554 exists precisely because an earlier attempt failed closed and dropped legitimate events. Uncertainty must accept. What the fix closes is the case where the store was authoritatively loaded for the active exhibit and holds no matching team — which previously accepted every foreign TeamCard for as long as the user stayed there. The first commit body claimed the opposite; that was caught in review and corrected, since a misleading explanation of a high-risk predicate is a defect in its own right.

08Where subagents pushed back

Five moments where an agent declined an instruction — mine or the plan's — and was right to. Recorded because in each case the obvious fix was the wrong one, and because two of them were corrections to me.

D — an implementer refused a brief that would have broken the error path

I told it to drop the marker's clear-at-start writes and set the marker on success only. It did that, then went one step further than instructed and added an explicit clear to both error callbacks — flagging the addition rather than burying it.

It was right, and the reasoning is subtle: the clear-at-start write had been passively doing the error path's job. Remove it alone, and a failed load following a successful load for the same exhibit leaves the marker confidently naming an exhibit whose store the error path just emptied — so the predicate would then reject every TeamCard for that exhibit until the next successful load. That is exactly the fail-closed mode the design exists to prevent. My instruction would have traded a transient over-acceptance for a persistent dropped-event bug. The re-review independently confirmed the addition is load-bearing.

D's spec — an implementer tested a different code path than I specified, correctly

I briefed a spec covering the predicate's authoritative branch: team resolves from the store to a different exhibit → reject. The implementer covered a different branch instead and explained why: that branch is byte-for-byte identical before and after the fix, so a spec on it could not fail against the pre-fix code — it would have been precisely the vacuous spec I'd warned it against in the same brief. Worse, the branch is unreachable for a foreign team anyway, since an earlier commit stops foreign teams entering the store at all.

I verified the byte-identical claim myself with git show before accepting it. The property I actually cared about — a foreign TeamCard must not reach the Wall's store — is pinned; just through the arm that genuinely decides it.

A reviewer refused to certify bug C's spec without testing the test

A trackBy spec can pass for the wrong reason: if the store emission never reaches the component, nothing rebuilds the row, and the panel stays open for reasons unrelated to the fix. Rather than reason about this, the reviewer patched the served bundle two ways — first reverting trackBy (spec failed at the panel assertion, correct symptom), then leaving the fix intact but emptying the SignalR handler (spec failed earlier, at the emission guard). That second run is the one that matters: it proves the spec cannot pass vacuously.

It also found that pointing trackByFn at a shared constant made the spec pass, because a constant key is more stable than the real fix — a useful reminder that the spec detects "no stable row identity", which is the actual defect.

§14 — the review caught a fail-closed filter

The first §14 implementation filtered TeamCard events with teamQuery.hasEntity(teamId), relying on the team store holding only the active exhibit's teams. The reviewer found that invariant is breakable: the store is never cleared on exhibit exit (unload() has no callers) and admin's loadByExhibitId writes the same store. During an A→B switch the store still holds A's teams — non-empty, so the getCount() === 0 fail-open escape never fired, and a legitimate exhibit-B event was dropped. Worse than the bug being fixed, and it contradicted the implementer's own claim that the worst case was "behaves like today".

That went into a fix round. Notably, the implementer declined the literal suggestion I passed along ("look the team up, fail open when not found") and explained why: in the steady state a foreign team is precisely the one absent from a correctly-loaded store, so naive fail-open-on-absent would have accepted every cross-exhibit event and silently un-fixed §14. It instead discriminates "absent because stale" from "absent because foreign" by asking whether the store holds any team of the active exhibit. The re-review verified both directions — legitimate B event accepted during the window, foreign event still rejected in steady state — and I had it assess that pushback on the merits rather than deferring to it.

§14 API half — declining to narrow two broadcasts

Your decision was "UI fix and narrower API broadcasts". For two of the three handlers, the honest answer was to change nothing — and I had explicitly made that an acceptable outcome rather than something to be worked around, because the alternative was worse. There is no join path for a compound exhibit+user group: MainHub.Join() adds only the userId group, and the client invokes switchTeam only on reconnect. A narrowed broadcast would have gone to nobody.

So UserArticleHandler and TeamCardHandler group addressing was left alone with the tracing to justify it, and the one provably safe change shipped (Distinct()). The UI filter is load-bearing and stands on its own. I'd rather report a partial API change I can defend than a thorough-looking one that silently breaks notifications.
