The leak spec was measuring nothing at all

This one is worth spelling out, because it "passed" for the wrong reason and would have kept passing through any real regression:

  1. It imported test from @playwright/test instead of the app fixtures, so it never got the pre-authenticated storageState — it was asserting against the Keycloak login page.
  2. Its cycle navigated /msels, /teams, /users — none of which are routes. Angular redirected all three to '', so the "cycle" just reloaded the dashboard.
  3. It called window.gc(), which is undefined unless Chromium is launched with --js-flags=--expose-gc (verified). The GC step was a no-op, so the numbers were unswept garbage — non-monotonic noise (3026 → 2257 → 5083 nodes).
  4. Worst: it measured across full page.goto calls. Each builds a new document and drops every node, so the metric resets and an SPA leak is invisible by construction. I proved this by injecting a deliberate 400-node-per-load leak — the old harness reported zero growth.

The rewrite forces a real GC via CDP HeapProfiler.collectGarbage and drives the app's own client-side section switching rather than goto.

Correction — my first replacement metric was also wrong, in two ways. I originally measured detached nodes as CDP Nodes minus document.querySelectorAll('*'). That is not a valid measure of retention: Nodes counts text and comment nodes and lags behind collection, while querySelectorAll('*') counts only elements in the main tree. It reported ~1364 phantom "detached" nodes on a page whose true detached count was zero, and drifted non-monotonically. The BP-11 figures I first recorded ("1017/render, attached pinned at 319") came from this — the direction was right, the magnitude was not.

My second attempt read the heap snapshot but filtered node names for a "Detached" prefix. Snapshot nodes aren't named that, so it silently matched nothing — it reported 0 detached nodes with 1000 deliberately detached ones on the page. Detachedness is a separate numeric node field (0=unknown, 1=attached, 2=detached).

Both mistakes were caught only because I injected a known 1000-node leak and checked the metric noticed: it now reads +1005 on injection and returns to baseline when the reference is dropped. The final spec also fits a slope over a series rather than trusting one before/after pair — baselines swing by hundreds of nodes between runs (1249 / 475 / 307 for the same page), so a single delta can't separate a leak from noise, and on leaking code it even came out negative once. A series additionally distinguishes a one-time warm-up step (one jump, then flat — which is what Data Fields turned out to be) from unbounded growth.

Application bugs found

Each was reproduced directly at the API and/or UI level before being written up; several were traced to the exact source line. Full evidence lives in blueprint/blueprint-app-bugs.md. Per the standing instruction, these are reported for fixing in the app rather than worked around in the tests.

BP-9 — A failed save is reported to the user as a success

Severity: high · MSEL → Config save path · blocks 1 test

With PUT /api/msels/{id} forced to 500: zero snackbars, zero [role="alert"], no error text — and Save Changes becomes disabled exactly as it does on success, because saveChanges() clears isChanged unconditionally. The edit is discarded and every UI signal says it saved.

BP-10 — xlsx import discards every scenario event's time

Severity: high · MselService.cs ~line 1141 · blocks 1 test

Import assigns DeltaSeconds = rowIndex * 60 unconditionally, never parsing the exported Delivery Time. A round-trip through Blueprint's own export/import silently rewrote 300s/900s to 60s/120s. Export is correct; the defect is purely on the read side.

BP-7 — Logout does not log out

Severity: high · ComnAuthService (shared crucible-common) · blocks 1 test

Polled over 15s after clicking Logout: the OIDC entry — access token included — remains in sessionStorage, there is no redirect to Keycloak's end-session endpoint, and the user stays authenticated. May affect other Crucible apps that log out the same way.

BP-5 — Scenario Events grid renders every cell blank

Severity: high · ScenarioEventService.GetByMselAsync · blocks 1 test

The list query includes SteamfitterTask but not DataValues, while the single-item query does include it. So GET /api/msels/{id}/scenarioEvents returns dataValues: [] and the grid — which resolves cells from that per-event collection — shows nothing, even though /dataValues returns the text correctly.

BP-11 — MSEL Info section leaked ~963 detached DOM nodes per render — FIXED

Severity: medium · msel-info.component.ts:326 · fixed; test now passes

dataFieldQuery.selectAll() was subscribed with no takeUntil(this.unsubscribe$), unlike all six of its siblings in the same constructor. It is an Akita store observable that never completes, so every Info render leaked a live subscription that pinned the destroyed component's DOM. ngOnDestroy does fire unsubscribe$ — this subscription just wasn't wired to it.

Fixed by piping it through takeUntil like its siblings: 6 insertions, 3 deletions, one file. A repo-wide audit found no other unguarded store subscription — the remaining bare .subscribe() calls are in providedIn: 'root' services that live for the app's lifetime, or hold Subscription handles they unsubscribe.

Verified A/B by rebuilding the served bundle both ways and fitting a slope of detached nodes against render count:

The spec was then re-run against the unfixed bundle to confirm it still fails at 970/render — a 19× margin over its threshold of 50. A regression test that cannot catch the regression is worthless, so this check matters more than the passing run.

BP-3 — A MSEL can be saved with an empty name

Severity: medium · UI + API · blocks 2 tests

No validator at either layer. With the form dirtied, clearing Name leaves Save enabled, shows no mat-error, PUTs 200, and persists name: "". A direct PUT with an empty name also succeeds, so a client-only fix would leave the API open.

BP-4 — GET /api/msels/{id} returns 500 + a stack trace for any unknown id

Severity: medium · MselService.GetAsync lines ~211, ~224-228

Two unguarded null dereferences on the not-found path. Wrong status code for a routine "not found", and the body leaks source paths, class names and line numbers to any authenticated caller. Expected 404 with no detail.

BP-1 — Teams grid does not refresh after a delete

Severity: medium · msel-teams component · blocks 1 test

DELETE returns 204 and the API confirms removal, but the row stays rendered — stable for over 15s, with no follow-up GET. The component neither updates local state nor refreshes via SignalR.

BP-8 — A MSEL accepts a negative duration (end before start)

Severity: medium · PUT /api/msels/{id} · blocks 1 test

durationSeconds: -86400 is accepted and persisted verbatim. The UI renders a "backwards" indicator, so the condition is detected for display but never prevented.

BP-6 — The API intermittently stalls >10s at two workers

Severity: low–medium · blocks no test

At --workers=2 one spec per run dies on a DELETE timeout, and which spec moves between runs — the signature of a shared-resource stall, not a spec defect. The same 10 specs pass in 32s sequentially, repeatedly.

BP-2 — PUT /api/teams/{id} silently discards unknown fields

Severity: low as a bug, but actively misleading

Returns 200 for a body containing organizationId and drops the field. Blueprint has no team↔organization relationship at all, so a test asserting only the status code passes while verifying nothing. Recorded as a missing feature, not a broken one.

Diagnoses that overturned an agent's conclusion

Every subagent claim was checked against git diff and a fresh run. Four conclusions were wrong in both directions — reported bugs that were test defects, and a "no app bugs" verdict that was hiding a real one.

"The Is-a-Template checkbox change doesn't persist" — test.fixme() Same root cause. Verified via API that isTemplate persists correctly on a full GET-then-PUT. Now passes.

Infrastructure

Shared helpers added to blueprint/test-helpers.ts

30 exported helpers total. New this pass, each verified against the live API:

  • createRenderableScenarioEvent() — the key one. A ScenarioEvent has no description column; its text lives in DataValue rows, and a MSEL created via API has zero data fields. This handles both, so a seeded event is actually visible.
  • seedMselDataFields(), listMselDataFields(), setScenarioEventFieldValue(), getScenarioEvent()
  • createUnit(), deleteUnit(), addUnitToMsel(), removeUnitFromMsel(), listMselUnits()
  • getMsel(), updateMsel() — GET-then-PUT merge, since PUT replaces the whole object

Teardown purge fixed twice

The safety-net purge was failing silently in two different ways depending on which specs a run selected — a CJS-wrapped module namespace, and an ESM SyntaxError: Cannot use import statement outside a module. It now falls back to a tsx subprocess, verified end-to-end with a canary record that previously leaked. It was also extended to purge leaked global units, which the MSEL purge cannot reach — a real leak (Create Catalog Test Unit) was found sitting in the dev database, polluting every MSEL's contributor picker.

A silently-vanishing test

One spec used test.skip('title', 'reason', callback) — not a valid Playwright signature. It removed the test from discovery entirely ("No tests found") and leaked a MSEL that only the global purge caught. Fixed to test.skip(true, reason) inside the body.

A second data-hygiene hole, found by an accident

A run I started with the wrong flag executed the Firefox project and I killed it mid-flight. That interrupted run left behind a Copy Inject Test Catalog and six inject types — and the leftover catalog then broke copy-inject on the next run: its Add Inject button resolved to a hidden one inside the stale catalog's collapsed panel (Received: hidden).

The cause is a CLAUDE.md violation: the admin-catalog specs clean up inline at the end of the test body rather than in an afterEach, so any mid-test failure leaks global admin records. The teardown purge covered MSELs and units but not catalogs or inject types, so nothing swept them. The purge now handles both, deleting catalogs before inject types (an inject type cannot be deleted while a catalog references it) — and on its first run it swept five inject types these specs leak even when they pass, so the hole was wider than the one interrupted run.

Chasing that further exposed something I could not fix, and it is worth being blunt about. Eleven specs in that directory share the same global catalog and inject-type lists, seed fixtures under fixed literal names, clean up by name pattern, and locate rows with roughly 77 positional .first()/.last() locators. That combination is only sound single-threaded: all 11 pass at --workers 1, and 2 fail at --workers 2.

I confirmed this is pre-existing by stashing my edits and running the unmodified files at both worker counts — same 2 failures. I also tried test.describe.configure({ mode: 'serial' }) across all eleven; it does not help, because serial mode orders tests within a file while Playwright still distributes files across workers. I removed it rather than leave a change that implies a fix it does not deliver.

A correction worth recording. My first pass at copy-inject removed 8 of its 14 sleeps and rewrote its panel locators. That regressed it — the spec then failed even at 1 worker, where HEAD passed 11/11. The sleeps were load-bearing for this shared-state directory. I reverted to HEAD and kept only two changes I could verify in isolation: un-swallowing a .catch(() => {}) that hid a failed save, and scoping one cell assertion to a visible match. The real fix is per-spec seeding with tempBlueprintName(), which is a larger change than this pass should absorb; it is written up in README.md so the constraint is discoverable rather than folklore.

How to reproduce these numbers

./run-tests.sh blueprint --browser chromium --workers 2 --no-check

Note --browser, not --project: run-tests.sh takes the former, and omitting it runs Firefox as well as Chromium.
