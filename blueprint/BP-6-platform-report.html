BP-6 — the SignalR fan-out is awaited on the HTTP request path

A stalled or frozen browser tab can block every write in the API. Found in Blueprint, fixed there, and then found to be identical in six sibling apps — because they all inherit the same publish path from Crucible.Common.EntityEvents. This document covers the mechanism, the measurements, the fix, the per-app footprint, and a concrete proposal for moving the solution into Crucible.Common so every app benefits at once.

1 · What happens

Any HTTP write to an entity that has a SignalR handler cannot return until every subscribed client has accepted the broadcast. One client that has stopped reading its socket is enough to stall writes for everyone.

The user-visible symptom is a save that hangs — potentially for as long as the socket takes to give up — while the rest of the app looks perfectly healthy. That asymmetry is the diagnostic signature and it is what made this hard to identify:

GET  /api/users -> 200 in 0.004s      # reads have no event handler: instant
POST /api/users -> stalls ~11s        # writes fan out to SignalR first

It is not a load problem. It reproduces with one non-draining subscriber, sequentially, on an otherwise idle box. It does not require a malicious client either — a laptop that sleeps with a tab open, a phone that loses signal, or a tab throttled in the background all present the same way to the server: TCP connected, window closed, never draining.

Why this deserves attention beyond a test-suite annoyance. The blocking is on the request thread, and it is unbounded — there is no timeout anywhere on this path. Under enough stalled clients the practical outcome is thread-pool starvation on writes while health checks and reads keep answering, so the service looks up to every monitor you have. In Blueprint's case a single suite run was enough to reach a state where aspire resource blueprint-api restart itself failed with "Failed to stop resource".

2 · Root cause

Three layers cooperate, and only the third is app-specific — which is exactly why the defect is uniform across apps.

Layer 1 — the shared interceptor publishes events inside SaveChanges

Crucible.Common.EntityEvents ships EntityEventInterceptor, which calls PublishEventsAsync from EF Core's SavedChangesAsync / TransactionCommittedAsync hooks. So event publishing is inside the unit of work, and therefore inside the request.

And there is a synchronous variant that is strictly worse. EntityEventInterceptor.SavedChangesInternal (the non-async path, line 87) does: 
PublishEventsAsync(eventData.Context, default).GetAwaiter().GetResult();
The same appears at line 168 for the transaction path. Any caller using synchronous SaveChanges() therefore blocks a thread-pool thread for the full duration of the SignalR fan-out, rather than merely awaiting it. Note also the default cancellation token: even the caller's cancellation does not apply.

Layer 2 — each app's DbContext dispatches through MediatR, awaiting each handler

Every app overrides PublishEventsAsync the same way. Verified identical in Blueprint, CITE, Gallery, Steamfitter, Alloy and Caster:

public override async Task PublishEventsAsync(IReadOnlyList<IEntityEvent> events, CancellationToken ct)
{
    var mediator = ServiceProvider.GetRequiredService<IMediator>();
    foreach (var evt in events.Cast<INotification>())
        await mediator.Publish(evt, ct);        // awaits every handler, in order
}

Layer 3 — the handlers await the SignalR send

This is the only part that varies, and only cosmetically. Two spellings, same semantics:

// Spelling A — Blueprint (pre-fix), CITE, Gallery
var tasks = new List<Task>();
foreach (var groupId in groupIds)
    tasks.Add(_mainHub.Clients.Group(groupId).SendAsync(method, dto, modifiedProperties, ct));
await Task.WhenAll(tasks);                     // <-- on the request path

// Spelling B — Steamfitter, Alloy, Caster
await _engineHub.Clients.Groups(GROUP_A).SendAsync(method, dto);
await _engineHub.Clients.Groups(GROUP_B).SendAsync(method, dto);   // sequential: worse

The key fact about SendAsync: it does not mean "fire off a message". It completes when the message has been written to each target connection's transport. A connection whose buffer is full applies back-pressure, and the returned task simply does not complete. There is no default timeout.

The conceptual error, stated plainly: notifying other clients is not part of the caller's unit of work, so it should never share the caller's lifetime. A write should be durable and acknowledged as soon as it is committed; whether some third party has yet received a courtesy notification is irrelevant to that acknowledgement.

3 · Measurements

Blueprint API, otherwise idle. Four subscribed WebSocket clients that complete the handshake, join their groups, then stop reading — i.e. four frozen tabs. 200 sequential writes.

medianp95p99maxstalls ≥150 ms
Before9 ms13 ms10,974 ms11,003 ms4 (worst 11.00 s)
After10 ms13 ms22 ms48 ms0

Reads answered in 3 ms throughout, before and after. Broadcast delivery after the fix was measured separately — HTTP-write → frame-received latency — at 20/20 delivered, median 4 ms, p95 8 ms. The fix relocates the fan-out; it does not drop it.

Reproducing this is genuinely tricky, and two obvious approaches give false negatives. Recording them because they cost real time:
  • Long polling does not work. A long-polling client that stops polling is reaped by the server and stops being a broadcast target — no stall, and a misleading "not reproducible".
  • Low volume does not work. 40 × 60 KB to one silent WebSocket sat under the combined server-send + client-receive buffer capacity. Four subscribers were needed.
  • Sampled logging hides it. One run reported max 11004 ms while every printed write showed 9 ms — the stall fell between samples. Log every write over a threshold, not every Nth.
  • Verify the precondition before trusting a negative. A separate probe confirmed that a reading client in the same groups does receive the frame — otherwise "no stall" might simply mean "nothing was ever sent there".
Harnesses are checked in at blueprint/bp6-harness/ (with a README): plain Node, no dependencies, hand-rolled WebSocket framing precisely so the client can stop reading on demand. They should move alongside the package if this proposal proceeds.

4 · The fix as implemented in Blueprint

Branch fix/bp-6-signalr-broadcast-blocks-writes in blueprint.api — 2 commits, 27 files, +497/−584.

A HubBroadcaster: a single-reader bounded-channel BackgroundService. Handlers hand it a broadcast and return immediately, so the fan-out leaves the request path entirely.

public interface IHubBroadcaster
{
    void Broadcast(IEnumerable<string> groupIds, string method, params object[] args);
}

Handler bodies become synchronous where nothing else is awaited:

// before
var tasks = new List<Task>();
foreach (var groupId in groupIds)
    tasks.Add(_mainHub.Clients.Group(groupId).SendAsync(method, user, modifiedProperties, ct));
await Task.WhenAll(tasks);

// after
_broadcaster.Broadcast(groupIds, method, user, modifiedProperties);

Design decisions worth defending

  • Bounded queue, DropWrite on overflow. Unbounded would trade a latency failure for a memory failure. Drops are logged (first, then every 100th). A dropped notification is self-healing because the UI re-reads on navigation — it is strictly less harmful than a hung save.
  • Per-send timeout. Each dispatch is bounded by BroadcastSendTimeoutSeconds (default 10). Without it, a non-draining client would park a worker forever — the original defect, merely relocated.
  • Bounded concurrency. A SemaphoreSlim (BroadcastMaxConcurrency, default 64) caps in-flight fan-outs, and dispatch is not awaited by the reader loop, so one slow client cannot stall the queue behind it.
  • Group ids are materialised at enqueue time. The caller's list may be backed by a scoped DbContext query; the worker runs after that scope is gone.
  • Group computation, DB queries and mapping were not touched. Handlers that still await a real query (e.g. Blueprint's BaseMselHandler with its Include chain) remain async.
Verification of the conversion itself: 51 SendAsync calls became 51 Broadcast calls — counts matching exactly across 25 handler files — with zero residual _mainHub references and a clean build. UserCreated was confirmed still arriving at a reading client with an identical payload. The full Blueprint Playwright suite (139 tests) shows no regression attributable to the change.

Known trade-off: ordering

Because dispatch is concurrent, two broadcasts for the same entity are no longer guaranteed to arrive in emission order. In practice the clients affected here are stores keyed by entity id (akita upsert), so a late-arriving stale update is a theoretical concern rather than an observed one — but it is a real semantic change and should be an explicit review point. If any app needs per-entity ordering, the queue can be sharded by group id with a per-shard reader.

183 SendAsync call sites in total, of which 51 are already converted in Blueprint. CITE and Gallery are near-verbatim copies of Blueprint's pre-fix code, so they would convert almost mechanically. Steamfitter, Alloy and Caster use sequential awaits, which are more exposed per request — two stalled sends serialise rather than overlap.

No app has solved this. I grepped all six apps plus libraries/ for any queued-broadcast abstraction — no matches. So there is no existing precedent to copy, and equally no competing pattern to conflict with.

But the pattern is not foreign to the platform. Blueprint already runs four producer/consumer queues drained by hosted services (IntegrationQueue, JoinQueue, AddApplicationQueue, XApiQueueService), and IntegrationService already sends SignalR from a background worker (IntegrationStatusUpdated). Caster has RunQueueService. The proposal generalises an existing in-house pattern rather than importing a new one.

6 · Proposal — Crucible.Common.SignalR

A new package alongside the existing four, so all apps get the fix by taking a version bump rather than by each re-deriving it.

Why a new package rather than folding it into EntityEvents

Crucible.Common.EntityEvents is deliberately transport-agnostic — its only dependencies are EF Core, DI and Logging abstractions, all with PrivateAssets="all". Adding SignalR to it would force an ASP.NET Core dependency onto every consumer of the events library, including any non-web consumer. No existing Crucible.Common package references SignalR. A separate package keeps that boundary intact and lets apps adopt independently.

What it would contain

src/Crucible.Common.SignalR/
├── src/
│   ├── Abstractions/IHubBroadcaster.cs        // void Broadcast(groups, method, args)
│   ├── HubBroadcaster.cs                      // bounded Channel + BackgroundService
│   ├── Options/SignalRBroadcastOptions.cs     // timeout / capacity / concurrency
│   └── Extensions/ServiceCollectionExtensions.cs
│                                              //   AddHubBroadcaster<THub>(...)
├── build/Crucible.Common.SignalR.props        // compiles contentFiles, per house style
├── README.md
└── Crucible.Common.SignalR.csproj

Registration would mirror the existing AddEntityEventInterceptor() / AddEventPublishingDbContextFactory<T>() convention, generic over the hub so each app keeps its own (MainHub, EngineHub, ProjectHub, …):

services.AddHubBroadcaster<MainHub>(o => { o.SendTimeout = TimeSpan.FromSeconds(10); });
One packaging detail that materially shapes the work. Crucible.Common.EntityEvents ships as a source distribution, not a compiled assembly: the csproj does <Compile Remove="src/**/*.cs" />, packs the files as contentFiles, and a build/*.props file compiles them in the consuming project. That is a deliberate house choice ("all code compiles in consuming project for easy debugging"). A new package should follow it for consistency — but it means consuming apps compile the source, so the library's language level and nullable settings must be compatible with every consumer, and a bug fix requires a package bump in each app rather than a runtime-only update. Worth an explicit decision: match the source-distribution style, or ship this one as a normal assembly.

Concrete steps, following the documented process

The repo's README.md already specifies how to add a package; these steps follow it rather than inventing a workflow.

1 · Land the abstraction in crucible-common-dotnet

dotnet new classlib -n Crucible.Common.SignalR, add to Crucible.Common.slnx, copy the license/readme handling from Crucible.Common.Authentication.csproj, and add Crucible.Common.SignalR to the packageName options in .github/workflows/release-package.yml — the README flags this as an easy step to miss, and without it releases silently exclude the package.

2 · Test it in test/Crucible.Common.Tests

The project already exists and the package grants it InternalsVisibleTo. The tests that matter are the ones that would have caught this defect, and they need a fake IHubContext whose SendCoreAsync never completes:

  • Broadcast returns before a non-completing send finishes — the core property.
  • A send that never completes is abandoned after the timeout, and logged.
  • Queue overflow drops rather than grows, and logs.
  • One stalled group does not delay a subsequent unrelated broadcast.
  • Shutdown drains or cancels cleanly without throwing.

3 · Prove it end-to-end in one app first — Blueprint

Blueprint is already converted, so switching it from its local HubBroadcaster to the package is a small, low-risk diff that validates packaging, registration and the source-distribution mechanics. Re-run the wedge harness to confirm the same before/after numbers through the packaged path, and re-run the 139-test suite.

4 · Convert the remaining apps, largest exposure first

Suggested order by call-site count and similarity: CITE (29) and Gallery (27) next, because they are near-verbatim copies of Blueprint's pre-fix shape and convert almost mechanically; then Steamfitter (31), Caster (25), Alloy (13), which need the sequential-await spelling rewritten; then Player VM (7). Each is an independent PR — the package makes them additive, not a big-bang migration.

The mechanical part is scriptable and should be: I converted Blueprint's 23 remaining files with a Python script that asserted every transformation and refused to write a file whose shape it did not recognise (it left zero files unconverted, and the 51 → 51 count match was the check). The same approach transfers, but each app still needs its own before/after measurement — the count match proves the edit, not the behaviour.

5 · Consider fixing the sync-blocking path in EntityEvents too

Independent of this proposal, EntityEventInterceptor's .GetAwaiter().GetResult() (lines 87 and 168) blocks a thread-pool thread on the whole publish chain for synchronous SaveChanges() callers, with a default cancellation token. The broadcaster removes the SignalR portion of that cost, but any other slow handler still blocks. Worth its own look.

Alternatives I considered and rejected

A · Fire-and-forget at each call site (_ = SendAsync(...))

Smallest possible diff, no new package.

rejected Unbounded — trades a latency failure for a memory/socket failure under many stalled clients, and swallows exceptions silently. Also has to be repeated correctly at 183 call sites, with nothing to enforce it.

B · Per-send timeout only, still on the request path

Add a CancellationTokenSource.CancelAfter to each SendAsync.

rejected Bounds the damage but does not remove it: every write still pays the timeout whenever a client is stalled. A 2 s cap on a 10-writes-per- interaction flow is still a visibly broken app.

C · Move publishing off the request path entirely, in EntityEvents

Have the interceptor enqueue events and publish them from a background worker, fixing all handler types at once, not just SignalR.

strongest long-term option — out of scope here This is arguably the correct fix, and it subsumes the broadcaster. But it changes the semantics of every event handler in every app simultaneously (transaction affinity, scoped-service lifetime, error handling, ordering), which is a much larger conversation. The broadcaster is compatible with it: if the interceptor later goes async, the broadcaster becomes redundant and can be removed without touching handler logic again.

D · Per-app local copies of HubBroadcaster

What exists today, in Blueprint only.

viable but poor Six near-identical copies drift. The fix is ~160 lines of concurrency code with real edge cases (bounding, timeout, shutdown) — precisely the kind of thing that should exist once, tested once.

7 · Risks, and what I would want reviewed

RiskMitigation / open question
Ordering is no longer guaranteed per entity, because dispatch is concurrent. Clients key stores by id, so late stale updates are theoretical here. If any app needs ordering, shard the queue by group id with a per-shard reader. Needs a decision, not an assumption.
Dropped notifications under sustained overload. Bounded by design and logged; UI re-reads on navigation. Capacity (10,000) is a guess and should be sized against a real busy exercise.
Source-distribution packaging couples the library's language/nullable settings to every consumer. Follow the house style for consistency, or make a deliberate exception for this package. Team call.
Behaviour change is invisible in normal testing — everything passes either way with healthy clients. The stalled-client harness must be part of the deliverable, not a one-off. Without it, a future refactor silently reintroduces this.
Player VM API was not measured, only read. Confirm before including it in scope; its handlers look the same but I have not run the harness against it.
My honest position. The defect is real, platform-wide, and measured — I am confident about that. The shape of the fix is a design choice I made alone under time pressure in one app, and it deserves scrutiny before it becomes a platform pattern: specifically the ordering trade-off, the drop-on-overflow policy, and whether option C (async event publishing in EntityEvents) is where the effort should actually go. If the team prefers C, my Blueprint branch is still useful as a measurement rig and a stopgap, and should be treated as a proposal rather than a merge candidate.
