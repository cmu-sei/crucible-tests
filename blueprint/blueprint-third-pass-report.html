BP-6 — fixed, on its own branch

Branch fix/bp-6-signalr-broadcast-blocks-writes in blueprint.api, based on the checked-out commit. Two commits, 27 files, +497/−584.

Root cause. Every entity event handler built a list of SendAsync tasks and did await Task.WhenAll(tasks). Those handlers run inside BlueprintContext.PublishEventsAsync, which SaveChangesAsync calls — so that await sat directly on the HTTP request path. An HTTP write could not return until every subscribed client had accepted the broadcast. A client that has stopped reading its socket does not fail fast: its transport buffer fills, TCP back-pressure stops the send completing, and the write blocks behind it. Reads have no such handler, which is exactly why they stayed instant and made this look like a random API stall.

Reproducing it took three attempts, and the first two negatives were misleading. A long-polling subscriber that stops polling gets reaped by the server, so it stops being a broadcast target — no wedge. A WebSocket subscriber that stops reading does hold the write, but 40 × 60 KB was under the combined socket-buffer capacity. Before trusting either negative, a separate check confirmed the precondition actually held: a reading client in the same groups does receive UserCreated, so broadcasts really were targeting the silent one. Scaling to 4 silent subscribers and logging every slow write is what exposed it — the earlier run had already recorded max 11004ms while every sampled write printed 9 ms, i.e. the defect was hiding between samples.

Before9 ms13 ms10,974 ms11,003 ms4 (worst 11.00 s)

Reads answered in 3 ms throughout, before and after — which is the asymmetry that defines this bug.

The fix. A new HubBroadcaster: a bounded-channel BackgroundService. Handlers hand it a broadcast and return, so notifying clients no longer shares the caller's lifetime. A stuck client can delay other broadcasts — bounded by SignalROptions.BroadcastSendTimeoutSeconds — but can no longer delay a write. The queue is bounded and drops the newest broadcast when full rather than growing without limit; drops are logged, and are self-healing because the UI re-reads on navigation.

All 25 handlers were converted: 21 used the task-list shape (46 blocks), and GroupHandler, GroupMembershipHandler and SystemRoleHandler awaited a single send directly (9 sends). 51 SendAsync calls became 51 Broadcast calls — the counts match exactly. Group computation, DB queries and AutoMapper mapping are untouched; handlers that still await a real query stay async. Delivery was re-verified after the change: UserCreated still arrives with an identical payload, and a follow-up measurement of HTTP-write → frame latency gave 20/20 delivered, median 4 ms, p95 8 ms. The fix moves the fan-out off the request path; it does not silence it.

The 81 sleeps — and the correction that mattered

The previous report was wrong about where they were. It said the residue was "concentrated in admin-inject-types-and-catalogs, where an earlier attempt to remove them regressed the directory — they are load-bearing there until BP-16 is fixed." That directory contained zero waitForTimeout/ networkidle — both now and at commit 6cc6dcc, the commit the report was written from. The residue was always in the SignalR (20), accessibility (19), integration (14) and performance (11) directories. Nothing was load-bearing, and nothing was blocked on BP-16.

The real obstacle was different and larger: almost every sleep sat inside a spec that could not fail. Removing a sleep meant first building the fixture that made the surrounding assertions mean something. Several patterns recurred:

  • Absence of data asserted as a pass. Both performance specs ended expect(hasMsel).toBe(false) with the comment "Document that no test data exists" — they passed because they found nothing, every run, because they navigated to /msels, which is not a Blueprint route.
  • Hardcoded pass values. The timeline spec's scroll measurement opened with if (!scrollContainer) return { fps: 60, dropped: 0, smooth: true }, so expect(scrollMetrics.smooth).toBe(true) was satisfied by a literal. Its "FPS" came from counting setInterval ticks, which measures the timer, not frame production. That claim was dropped rather than dressed up.
  • Assertions on always-true expressions. expect(afterHover).toBeTruthy() on an object literal; expect(apiCalls.length).toBeLessThan(100) against a list that was always empty.
  • Comma-joined text= selectors. Playwright's text= engine cannot be comma-combined, so those locators match zero elements. This one root cause silently disabled controls in six specs, including both admin-navigation specs, which therefore never exercised the UI path they claimed to test.
  • Dead code behind selectors that match nothing. Measured on the dashboard: button:has-text("Create"), …("Add"), …("New") matches 0 elements, as does the theme toggle locator — so those blocks, and their sleeps, never ran at all.

A metric that reported a WCAG failure that did not exist

Making the dark-theme contrast block reachable immediately reported 1.61:1, an apparent WCAG AA failure. It was the metric, not the app — the same class of trap already recorded under BP-11 and BP-13. The old helper returned getContrastRatio(backgroundColor, color) for the first element with a non-transparent background, which here is a container that renders no text of its own and merely inherits color: rgb(0,0,0). Comparing an unused text colour against a backdrop is meaningless. Measuring every element that actually owns a text node, against its effective backdrop: 5.54 (toolbar), 10.04 and 11.84 (card title and subtitle) — all passing. No bug was filed. The new metric was then proved able to fail by injecting a #7a7a7a-on-#777 element, which it caught at 1.04:1.

Two new application bugs

Both were found because a spec started measuring something real. Per AGENTS.md they are reported, not worked around.

BP-17 — permissions are refetched once per component mount

medium · blueprint.ui/src/app/data/permission/permission-data.service.ts

PermissionDataService is a providedIn: 'root' singleton that stores permissions in _permissions but never consults it before fetching, and 15 components call load() in ngOnInit. Measured across four page loads: /api/me/systempermissions requested 11 times (next busiest endpoint: 4), of which 7 were rapid duplicates fired near-simultaneously by components mounting together.

The spec asserts the per-endpoint cap at <12 — just above the measured 11, and deliberately not 11, so it does not encode today's defect as the expectation — and splits the duplicate check so a new source of duplicates fails while the documented one cannot mask it.

BP-18 — a client can stop receiving a MSEL's updates for the rest of its session

medium · signalr.service.ts + home-app.component.ts · currently failing 2 specs

The user is shown a stale grid indefinitely: their own edits and everyone else's never arrive, nothing reports a problem, and nothing retries. A reload fixes it, so it reads as "real-time collaboration sometimes just doesn't work".

Three independent unguarded paths in the client-side group-join bookkeeping: join() no-ops if the connection is not yet Connected and never retries; selectMsel() retries only the not-connected case and falls off the end of the method when connected but not joined; and onreconnected re-joins the base groups but never re-applies the MSEL selection, while server-side SelectMsel removes the connection from every MSEL group before re-adding one. Every invoke on these paths discards its result, so a failed join looks identical to a successful one.

Which of the three the load triggers is not pinned down, and the entry says so rather than guessing. What it does record is everything ruled out — API broadcast loss/delay (20/20 delivered, median 4 ms), the BP-6 wedge (writes 201 in 7–14 ms afterwards), the BP-6 broadcaster change (zero drops/timeouts logged, and an unmodified spec fails identically), the specs contending with each other (3/3 pass together), loss at page load (both windows are provably in the group at test start), navigation (survives 3/3), and cross-window eviction (4/4).

Three findings that came from checking a negative result rather than accepting it

  • The BP-6 harness "NOT wedged" verdict was wrong twice. Before trusting it, a separate probe confirmed a reading client in the same groups does receive the broadcast — so the negative was about scale, not mechanism. Sampling was then found to be hiding an 11-second stall.
  • The presence spec could never have passed as written. MainHub.GetPresence filters c.UserId != userId, so a second window signed in as the same admin is excluded from its own presence list by design. And group membership comes from units, not teams — GetMselIdList reads UnitUsers → MselUnits and never consults teams. Seeding a team produced zero chips, which is how this was found.
  • Blueprint has no conflict detection, and the old spec asserted it did. No concurrency token exists anywhere. Measured: two clients read the same DataValue, both PUT it, the second from a stale copy → 200, 200, last write wins silently. The old assertion expect(hasConflictUI || hasError).toBeTruthy() passed only by accident, because its locator list included bare [class*="error"] and [class*="warning"] matches that hit ordinary Material classes. The spec now asserts the true contract — last write wins, and both windows converge with no reload.

  • 1 flaky spec in the final run (Upload MSEL from File, passed on retry). It also appeared as Import MSEL from Excel and Delete MSEL Page in other runs — a rotating single flake in the import/upload area, not yet diagnosed.

  • BP-6 is unmerged on fix/bp-6-signalr-broadcast-blocks-writes. The suite's current numbers depend on it: the running API was rebuilt and restarted from that branch.
Two caveats worth stating plainly. blueprint.ui remains on the local, unpushed branch fix/msel-info-datafield-subscription-leak (the BP-11 fix), and blueprint.api is now on the unpushed BP-6 branch — so the suite's green state depends on two unpushed application changes. And concurrent Blueprint suite runs against one stack still sabotage each other: the globalTeardown purge deletes every row matching the generated name shape, including another in-flight run's fixtures. Run the suite one at a time.
