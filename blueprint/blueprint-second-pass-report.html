The requested finishing condition was not met, and I want to be direct about why. Five consecutive runs with identical results is not currently reachable — not because of the tests, but because of BP-6: the Blueprint API wedges every write once a SignalR client connection goes stale, while reads stay instant. On a healthy API the suite is 125 passed / 0 failed / 14 skipped, reproduced many times including once at 125/125 with zero retries and once against a completely fresh database. Runs that overlap a wedge lose 2–3 specs to write timeouts. Details below.

First: the previous pass's numbers did not reproduce

The prior report claimed 117 passed / 0 failed at 2 workers. A clean run at session start gave 112 passed / 1 failed / 4 flaky / 19 skipped — with the failures clustered exactly where that same report's "needs --workers 1" section predicted they would be.

So the first task was an honest baseline. Two accounting rules followed throughout, because both were being violated:

  1. A run's summary counts a flaky retry as "passed." Ran 139 tests: 125 passed can conceal three retries. Every figure here is read from results.json — expected / flaky / unexpected / skipped.
  2. A green test is not evidence. Every spec rewritten or newly written was sabotaged — its key precondition withheld — and confirmed to fail before being trusted.

The real problem: tests that could not fail

Most of this session was not repairing broken tests. It was finding tests that passed while asserting nothing — strictly worse than a red test, because they report a safety that does not exist.

One root cause behind most of the self-skips: selectors of the form text=A, text=B. Playwright's text= engine cannot be comma-combined, so those locators match zero elements — which silently triggered the test.skip() bail-out that made the spec report green.

Three helper defects that disabled 17+ specs at once

createScenarioEvent never sent scenarioEventType

17 specs affected · fixed

EventType starts at 10 (Inject=10, Information=20, Facilitation=30), so omitting the field persists 0 — not an enum member. The grid chooses a row's columns by matching that value against those three members, so with 0 it renders no cells at all, however good the DataValues are. Every spec seeding through this helper could only assert row presence. Verified live: the API echoes back "scenarioEventType": 0.

Also removed description and moveNumber from its options — neither exists on ViewModels/ScenarioEvent.cs, so both were silently dropped. Three specs passed moveNumber: 1, which read like a precondition while doing nothing.

seedMselDataFields depended on a pre-existing Standard MSEL row

every scenario-events / playbook / event-detail spec · fixed

It cloned that MSEL's 13 DataFields, but nothing in the suite creates it — so the whole block depended on the current database shape, exactly what CLAUDE.md forbids, and all of it would have failed in beforeEach against a fresh database. The 13 fields are now declared literally.

The teardown purge matched almost nothing

11 leaked units + 5 leaked MSELs found on a live stack · fixed

It filtered on the literal prefix TestBP- plus a hand-maintained allowlist, while the specs generate ~50 different prefixes (DeleteUnit-, EditUnit-, SearchMatch-, ViewList1-, …). Replaced with a match on the shape tempBlueprintName() emits (/-\d{13}-\d{1,6}$/), so a new prefix is swept automatically instead of leaking until someone remembers the allowlist.

Root causes, not workarounds

The one hard failure in the baseline was a cascade delete

The previous pass concluded admin-inject-types-and-catalogs was "only sound single-threaded", blamed ~77 positional locators, and documented a --workers 1 requirement. That was not the mechanism. Deleting an inject type cascade-deletes every catalog that references it:

POST /api/injectTypes {name: ZZCascadeIT} -> 201 id=IT POST /api/catalogs {name: ZZCascadeCat, injectTypeId: IT} -> 201 id=CAT DELETE /api/injectTypes/IT -> 204 GET /api/catalogs/CAT -> 204 (empty) <-- gone

Five specs chose their inject type with page.locator('mat-option, [role="option"]').first() — the globally first option, frequently a sibling spec's. That sibling's cleanup then destroyed this spec's catalog mid-test. Each spec now selects the inject type it created itself, and the directory runs at 2 workers.

The launch flow is empty by design

Four specs self-skipped waiting for launch cards. MselService.cs:2203:

// DISABLED: Auto-discovery based on email domain matching // Users must now use invitation links directly to launch MSELs return new List<ViewModels.Msel>();

GET /api/my-launch-msels returns [] unconditionally. A deliberate product decision — so no bug filed — but it means no card can ever render. Those specs now assert that contract, and will fail if auto-discovery is ever switched back on.

Joining is gated twice

my-join-msels needs status: Deployed + a non-null PlayerViewId + team membership. But POST .../join separately checks the Player views the user is genuinely in, and otherwise falls to the invitation branch with 403. A joinable-looking MSEL is not a joinable MSEL.

Application bugs

Five new, one materially re-diagnosed, one extended. Each was reproduced directly and traced to a source line before being written up — and two agent-reported "bugs" were rejected after failing verification.

BP-6 — every write wedges once a SignalR connection goes stale; reads stay instant

Severity: high · UserHandler.cs:41-56 · blocks the 5-run gate

Originally filed as "the API intermittently stalls under light concurrency", diagnosis unknown. Reproduced with a single curl, sequentially, zero browsers running:

GET /api/users -> 200 in 0.004s POST /api/users -> 000 after 12s (also 15s, 20s, 25s caps)

Ruled out with evidence: not the DB (7 connections, 0 blocked locks, no query older than 0s); not the service method (Add + SaveChangesAsync + re-GET); not load (load average ~1 on 16 cores); not test concurrency (one curl).

The cause is on the request path — the handler awaits the SignalR fan-out before the HTTP response:

tasks.Add(_mainHub.Clients.Group(groupId).SendAsync(method, user, ..., cancellationToken)); await Task.WhenAll(tasks); // <-- on the HTTP request path

One half-dead client connection holds the writer hostage. Reads have no such handler, which is precisely why they stay fast.

It is process state: on a freshly started API the same POST is 201 in 8–62 ms; after a few suite runs it hangs, with no test change in between — measured three separate times. Once wedged, aspire resource blueprint-api restart can itself fail with "Failed to stop resource". And it degrades: early in the session it took 3–4 full runs to wedge; by the end, 1–2. Two measurement claims in existing entries were wrong, in ways that mattered.

BP-13's predecessor claimed body.scrollWidth was "~466px at a 375px viewport". Measured directly: 375. Its assertion expect(bodyWidth).toBeLessThanOrEqual(375) would therefore have passed — the metric could not detect the defect its own comment described. (466 is the right edge of one overflowing element.)

BP-12's predecessor claimed the app "does not use semantic HTML heading elements (h1–h6)". The templates actually contain 3 <h1>, 10 <h2>, 4 <h3> and 5 <h4> — they are simply absent from the main surfaces. The landmark half of the claim was correct.

This is why every skipped assertion here was run un-skipped and confirmed to fail. A skip whose assertion is wrong hides the defect just as effectively as a deleted one.

Verification

Fresh database — the real test of self-seeding

aspire stop → remove the crucible-postgres container and its volume → aspire start → delete .auth/. The fresh DB holds only 3 migration-seeded MSELs, 0 units, 1 user:

139 tests: 125 passed, 0 failed, 14 skipped

That is the proof that every spec seeds the data it asserts on. (The suggested minikube/clean-postgres.sh does not apply — it looks for a Kubernetes StatefulSet via kubectl and exits early under Aspire, which runs Postgres as a Docker container.)

Two caveats worth stating plainly.

blueprint.ui is checked out on the local, unpushed branch fix/msel-info-datafield-subscription-leak (the BP-11 leak fix from the previous pass). The suite's green state depends on an unpushed application change. On main, memory-leak-detection fails at ~963 detached nodes per render — correctly, because it is a real leak.

Concurrent Blueprint suite runs against one stack sabotage each other. The globalTeardown purge deletes every row matching the generated-name shape, including another in-flight run's fixtures. Run the suite one at a time.

How to reproduce

./run-tests.sh blueprint --browser chromium --workers 2 --no-check

Read test-results/results.json rather than the summary line — the summary counts a flaky retry as passed. If a run shows write timeouts, restart blueprint-api and re-run before suspecting the specs.
